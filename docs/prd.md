# CROXER 제품 요구사항 정의서

- 작성일: 2026-11-14
- 문서 상태: 논의된 기획 기반 초안
- 목적: 바이브코딩으로 UT용 프로토타입을 구현하기 위한 제품·기능·화면·상태 기준 정의
- 적용 범위: 서비스의 핵심 방향과 첫 UT에 필요한 구현 요구사항

> 이 문서의 요구사항은 구현 완료를 의미하지 않는다. 서비스의 전체 방향과 첫 UT 구현 범위를 구분하며, 논의되지 않은 정책·기술 선택·수치 목표는 확정하지 않는다. 미정 사항은 11장에 모아 두었다. 구체적인 인물, 날짜, 대화 전문과 과제별 진행 순서는 별도의 UT 시나리오 및 데이터 문서에서 관리한다.

## 1. 제품 개요

### 1.1 서비스 정의

CROXER는 여러 역할과 활동을 병행하는 크로스 플레이어의 활동 맥락을 이어주고, 현재 활동과 상황에 맞춰 필요한 정보와 기능을 구성하는 **다이나믹 UI(Dynamic UI)**를 제공하는 Agentic AI 서비스다.

### 1.2 해결할 문제

여러 활동을 병행하는 사용자는 활동을 전환할 때마다 흩어진 자료와 대화를 찾고, 이전 진행 상황을 떠올리며 필요한 도구를 다시 준비해야 한다. 갑작스러운 일정 변화가 발생하면 다른 활동과 마감에 미치는 영향도 직접 확인해야 한다.

CROXER는 활동별 맥락을 유지하고 필요한 정보와 기능을 준비해, 반복적인 확인·준비와 활동 전환에 드는 부담을 줄인다.

### 1.3 대상 사용자

학업, 콘텐츠 제작, 커뮤니티 운영 등 여러 직업과 활동을 병행하는 크로스 플레이어를 대상으로 한다. 새로운 활동을 시작하지 못하는 문제보다, 이미 수행 중인 다양한 활동을 관리하고 전환하는 데 어려움을 겪는 사용자를 중심에 둔다.

### 1.4 제품 목표

| 목표 | 제공할 경험 |
|---|---|
| 활동 전환 부담 감소 | 관련 자료와 이전 진행 상황을 다시 찾지 않고 이어서 활동함 |
| 현재 활동에 집중 | 브리핑에서 맨 위에 둔 활동을 홈에서 먼저 확인함 |
| 상황에 맞는 화면 제공 | 활동 목적에 맞춰 필요한 정보·기능·배치가 달라짐 |
| 맥락을 반영한 AI 지원 | 활동 조건과 일정, 작업 패턴을 고려한 제안을 확인함 |
| 사용자 주도권 유지 | AI의 위임 수준을 설정하고, 제안 수락과 활동 전환을 직접 선택함 |

정량 KPI와 목표 수치는 아직 정하지 않았다. 첫 UT에서는 기능 이해와 사용 과정의 어려움을 중심으로 검증한다.

## 2. 핵심 개념과 용어

| 용어 | 정의 |
|---|---|
| 역할 | 활동을 수행할 때의 사용자 역할. 학생·편집자·러닝 크루장 등 |
| 활동 | 역할에 속해 지속적으로 관리하는 단위. 프로젝트·촬영·러닝 등 |
| 일정 | 활동을 수행하기로 정한 시간과 진행 상태 |
| 할 일 | 활동 안에서 지금 수행해야 할 구체적인 일 |
| 자료 | 활동에 연결된 문서·레퍼런스·메모 등의 정보 |
| 활동 기억 | 특정 활동에 적용되는 사용자의 조건과 선호 |
| 맥락 | 활동을 이어가기 위해 필요한 자료·대화·일정·진행 상황·활동 기억 |
| AI 작업 | AI에게 맡긴 업무. 사용자 일정의 진행 상태와 별도로 관리 |
| 위임 수준 | AI가 업무를 어느 단계까지 진행할지 정하는 설정 |
| 다이나믹 UI | 활동과 상황에 맞춰 정보·기능·화면 구성이 달라지는 인터페이스 |

역할과 활동은 구분한다. 역할 표시 이름이 바뀌더라도 동일한 역할의 식별자는 유지한다. 사용자 화면에서는 활동 안의 구체적인 일을 ‘할 일’로 표현하고, UT의 ‘Task’는 테스트 과제를 뜻한다.

## 3. 제품 범위

### 3.1 첫 UT 구현 범위 (간단 UT)

첫 UT는 전체 서비스 대신 **정해진 활동 흐름**을 구현한다. 참가자가 브리핑에서 정한 순서에 따라 역할·활동 화면이 이어진다. 활동 순서, Task 번호, 종료 상태의 기준은 [간단 UT 활동 순서와 구현 범위](ut-activity-flow.md)이고, 시작 데이터와 ID는 [UT 데이터 베이스라인](ut-data-baseline.md)을 따른다.

| 영역 | 구현 내용 | 관련 기능 |
|---|---|---|
| 브리핑 | 활동 5개 표시. 01~03(리서치·촬영·러닝)만 순서 변경과 저장, 04·05(구독 연장·팀플회의)는 고정. 확정한 순서가 활동 진입 순서가 됨 | F-03 |
| 홈 | 현재 활동 카드에서 활동 화면으로 진입하는 최소 화면 | F-04 |
| 활동 화면 | Task 4 리서치 자료 검토, Task 6 강변 촬영과 비 알림·대안 대화, Task 8 러닝 문의·코스 선택·공지, Task 9 러닝 중 AI 작업 요청 | F-05·F-07·F-09·F-10 |
| 활동 전환 | 한 활동의 흐름을 마치면 전환 패널로 다음 순서의 활동 안내, 유지 또는 전환 선택 | F-06 |
| 스케줄 | 진행 완료·진행 중·진행 후 영역, AI 백그라운드 실행 상태 구분, 사용자 지정 순서 | F-11 |
| 진행자 패널 | 참가자 초기화, 돌발 상황 수동 발생, 막힌 과제의 다음 시작 상태로 이동 | 8.2 |

### 3.2 전체 기획에 포함되지만 첫 UT에서 제외하는 범위

- 셋업 전체: 서비스 미리보기, 역할·활동 등록, 활동 상세·목표 입력, 위임 수준·알림 설정(F-01·F-02). 역할과 활동은 초기 데이터로 미리 등록한다.
- 활동 기억 저장·수정과 이를 반영한 제안(F-07의 활동 기억 부분).
- 일정 시각을 실제로 바꾸는 일정 조정·교체(F-08). 첫 UT에서 일정 시각은 브리핑 순서 변경 외에는 바뀌지 않는다. 단, Task 6의 강변 유지 분기에서는 일정 조정 대화와 교체 제안·완료 화면을 보여줄 수 있다(데이터는 바꾸지 않음, F-08 참고).
- AI 작업 결과의 홈·상세 UX 확장(F-10의 일부). 단, Task 9(`job-shoot-extra`)는 첫 UT에서 요청 → 실행 중 → 완료까지 진행하며, 완료 시 연결 자료는 기존 공개 규칙을 따른다.
- 리포트와 피드백(F-11의 리포트 부분).
- 구독 연장·팀플회의 활동의 화면. 브리핑과 스케줄 목록에만 남은 활동으로 표시한다.

- 외부 계정을 실제 연동해 활동을 자동으로 발견하는 기능.
- AI가 실시간으로 새로운 화면 구조를 생성하는 기능.
- 위임 수준에 따라 실제 실행 권한과 동작이 달라지는 기능.
- 알림 설정에 따라 실제 알림 전달 시점이 달라지는 기능.
- 별도 승인 대기 목록, 구독 결제 화면, 회의 녹음 화면과 시나리오.
- 음성 입력. 첫 UT의 입력은 텍스트만 사용한다.
- 위임 수준·알림 설정의 상세 규칙(유형별 토글 조합, 직접 변경 시 유형 표시, 업무별 위임 설정)과 설정 변경 화면.
- 주간·시즌 리포트의 상세 기능.
- 실제 외부 메시지 전송, 실시간 위치 공유·센서 측정 연동.

첫 UT의 AI 응답·검색 결과·추천·측정값에는 준비된 가상 데이터를 사용한다. 실제 외부 데이터 분석이나 AI의 범용 추론 성능을 검증하는 것으로 해석하지 않는다.

### 3.3 설정 기능의 구현 한계

위임 수준과 알림 방식 설정은 첫 UT에서 구현하지 않는다. 공지 발송과 AI 작업 요청은 사용자의 명시적 확인을 거친다. 이후 설정을 구현할 때는 선택·저장 경험부터 만들고, 후속 동작에 반영되지 않는다는 사실은 진행자가 말로 안내하며 화면 문구는 넣지 않는다.

## 4. 정보 구조와 핵심 흐름

### 4.1 정보 구조

| 영역 | 주요 화면·정보 |
|---|---|
| 시작 | 서비스 미리보기, 역할·활동 등록, 활동 상세, 위임 수준, 알림 설정 |
| 홈 | 대표 활동 카드, AI 조언, AI 작업 상태·결과 |
| 활동 | 활동별 자료·기능, AI 채팅, 제안 검토, 활동 기억 |
| 스케줄 | 오늘·내일 일정, 순서와 진행 상태 |
| 리포트 | 오늘 리포트, 주간·시즌 리포트 확장 방향 |
| 설정 | 위임 수준·알림 방식 변경 방향. 변경 화면은 첫 UT 범위 밖 |

### 4.2 핵심 흐름

활동 등록·기본 설정 → 오늘의 브리핑 → 홈에서 활동 확인 → 활동 수행 및 AI 지원 → 다음 활동으로 전환 → 스케줄·리포트 확인

**첫 UT 흐름:** 브리핑에서 01~03 순서 확정 → 첫 번째 활동 수행 → 전환 패널로 다음 활동 → 세 활동을 모두 마침 → 스케줄에서 종료 상태 확인. 러닝 흐름에는 위치와 관계없이 Task 8 → Task 9가 이어진다.

활동 전환 제안에서 ‘유지하기’를 선택하면 현재 역할을 유지한다. 일정 변경 제안을 수락하지 않으면 기존 일정 시각을 유지한다. 위임한 AI 작업이 완료되어도 역할이 자동으로 바뀌지 않는다.

## 5. 기능 요구사항

아래 기능은 서비스 전체 방향이다. 첫 UT에서 구현하는 부분은 3.1, 제외하는 부분은 3.2를 따른다. 두 내용이 다르면 3.1·3.2와 [간단 UT 활동 순서와 구현 범위](ut-activity-flow.md)가 우선한다.

### F-01. 역할·활동 등록 및 상세 설정

**목적:** 관리할 활동과 활동별 맥락을 설정한다.

- 셋업은 등록된 역할·활동이 없는 상태에서 시작한다. 첫 UT에서는 셋업을 구현하지 않고 역할·활동을 초기 데이터로 미리 등록한다.
- 사용자가 역할을 등록하고 해당 역할에 활동을 연결한다. 자연스러운 별칭은 같은 역할로 인정한다. 준비 데이터에 역할·활동별 별칭 키워드를 두고, 입력이 키워드와 맞으면 같은 데이터로 연결한다. 맞는 키워드가 없으면 준비된 선택지를 보여준다.
- 등록한 활동에는 준비된 일정과 자료를 동일한 활동 식별자로 연결한다. 촬영·러닝·자료 정리는 역할 등록 후 제공되는 예시 활동이다.
- 활동 목록에서 상세 화면을 열어 활동 정보를 확인·수정한다.
- 상세 화면에는 활동명, 역할, 활동 설명, 연결할 자료, 목표 입력 영역을 제공한다.
- 상세 확인·수정과 목표 입력은 한 화면에서 처리한다. 목표만 입력하기 위해 활동별로 다시 순회하는 단계는 만들지 않는다.
- 목표는 자유로운 문장으로 입력할 수 있게 한다.
- 필수 입력값은 역할 이름과 활동 이름이다. 설명·자료·목표는 비워도 저장할 수 있다.
- 변경값은 `저장`을 눌렀을 때만 반영한다. 취소하면 이전 값으로 돌아간다.

**확인 기준:** 등록·수정한 활동 정보가 목록과 상세 화면에서 일치하고, 다른 활동의 자료와 섞이지 않는다.

### F-02. 위임 수준 및 알림 설정

**목적:** 사용자가 AI의 관여 수준과 알림 방식을 설정한다.

| 위임 수준 | 서비스에서의 의미 |
|---|---|
| 제안만 받기 | 다음 행동을 제안함 |
| 결과까지 준비하기 | 자료·초안·변경안을 준비함 |
| 확인 후 실행하기 | 준비한 내용을 보여주고 사용자 확인 후 실행함 |

- 업무 예시는 제공하되, 방대한 업무 목록을 모두 선택하도록 요구하지 않는다.
- 업무별로 다르게 설정하는 방향은 유지하되, 처음 구현할 때는 전체에 하나의 위임 수준을 선택한다.
- 알림 유형은 ‘집중 우선·균형 있게·놓치지 않기’로 구성한다.
- 유형과 상황별 토글을 같은 화면에 배치하고, 유형을 선택하면 토글이 즉시 바뀐다.
- 유형별 토글 조합과 직접 변경했을 때의 유형 표시 규칙은 첫 UT 범위 밖이다. 구현 담당자가 단순한 조합으로 정한다.
- 설정 이후 변경할 수 있는 방향을 유지한다. 변경 화면은 첫 UT 범위 밖이다.

**확인 기준:** 선택 상태가 시각적으로 드러나고 저장된다. 실제 후속 동작에 적용되는 범위는 3.3을 따른다.

### F-03. 오늘의 브리핑

**목적:** 하루의 예정된 활동을 파악하고 순서를 조정한다.

- 오늘 활동의 일정 시각, 할 일, 역할 또는 소속 활동을 간략하게 보여준다.
- 사용자가 활동의 표시 순서를 바꾸고 저장할 수 있다. 첫 UT에서는 01~03(리서치·촬영·러닝)만 서로 바꿀 수 있고(6가지 배열), 04·05(구독 연장·팀플회의)는 이동 핸들 없이 뒤에 고정한다. 다른 카드를 04·05 자리로 옮길 수도 없다.
- 확정한 순서가 활동 진입 순서와 역할 화면 순서가 된다.
- 바꾼 순서는 스케줄 화면에도 반영한다. 번호와 일정 시각은 자리에 고정되어, 순서를 바꾸면 그 자리에 온 활동이 자리의 시각을 갖는다. 04·05는 자리와 시각이 그대로다.
- 저장된 활동 기억이 있는 경우 해당 활동의 브리핑에 반영한다.
- 서비스 미리보기에서 조작한 상태는 셋업에 이어받지 않는다.

**확인 기준:** 순서를 바꾸면 번호와 시각은 자리에 남고 활동 카드만 옮겨지며, 다른 화면에서도 저장된 순서와 그에 맞는 시각을 확인할 수 있다.

### F-04. 현재 활동 중심의 홈

**목적:** 지금 확인하고 시작할 활동을 빠르게 파악한다.

- 대표 활동 카드를 화면 중심에 배치한다.
- 카드에는 역할·활동명·지금 할 일·시각 또는 남은 시간·제공될 정보와 기능의 개요를 보여준다.
- 카드를 선택하면 해당 활동 화면에 진입한다.
- 브리핑에서 맨 위에 올린 활동을 홈에서도 먼저 보여준다.
- 상단 세포·선은 대표 활동의 진행과 마무리 시점을 표현한다. 전체 일정 흐름과 단일 활동 진행도를 혼용하지 않는다.
- 사용자가 해야 할 일과 AI가 준비한 결과·진행 중인 작업을 구분한다.
- AI 작업은 대기·실행 중·완료 상태를 표시한다.
- 홈의 펼쳐진 ‘오늘의 스케줄을 확인해 보세요’ 안내를 선택하면 스케줄 화면으로 이동한다.

**확인 기준:** 사용자 일정의 진행 상태와 AI 작업 상태가 서로 다른 정보로 인지되며, 카드에서 예상한 활동 화면으로 진입한다.

### F-05. 다이나믹 UI

**목적:** 활동의 수행 목적과 현재 상황에 맞는 화면을 제공한다.

다이나믹 UI는 역할별 색상이나 제목만 바꾸는 기능이 아니다. 같은 서비스 안에서도 활동에 필요한 자료, 조작 도구, 정보의 우선순위와 배치를 달리해 사용자가 필요한 일을 이어가게 한다.

| 활동·상황 | 주요 정보 | 주요 기능 |
|---|---|---|
| 리서치 검토 | 기존 문서, 추가 조사 작업 상태 | 자료 열람, 목록 복귀 |
| 촬영 준비 | 촬영 레퍼런스, 메모, 날씨 영향 | 자료 확인, 조건 전달, 대안 검토 |
| 일정 조정 | 기존·변경 일정과 제안 근거 | 변경 수락, 보류 또는 닫기 |
| 러닝 문의 대응 | 공통 문의, AI 판단, 코스 후보 | 후보 비교, 코스 선택, 공지 확인·발송 |
| 러닝 측정 | 경과 시간, 거리, 페이스, 심박수 | 측정 시작·일시 정지, AI 업무 요청 |

- 첫 UT에서는 미리 설계한 화면과 컴포넌트를 활동·상태에 따라 표시한다.
- 활동 전환 후에도 해당 활동의 자료, 기억, 진행 상황은 유지한다.
- 새로운 상황이 생기면 그 활동 안에서 필요한 정보와 선택지를 제공한다.
- UI 변화 자체가 일정 완료, 제안 수락, 외부 실행을 의미하지 않는다.

**확인 기준:** 활동별 정보와 기능이 실제로 달라지고, 활동을 다시 열었을 때 저장된 맥락을 확인할 수 있다.

### F-06. 역할·활동 전환

**목적:** 다음 활동으로 넘어가는 이유와 변화를 알리고 전환의 주도권을 유지한다.

- 다음 활동을 시작할 시점에 전환 패널을 제공한다. 첫 UT에서는 한 활동의 UT 흐름을 마치면 전환 패널이 브리핑 순서상 다음 활동을 안내한다.
- 패널에서 현재·다음 역할과 활동의 관계를 보여준다.
- 사용자는 현재 활동을 유지하거나 다음 활동으로 전환할 수 있다.
- 전환을 선택하면 역할 표시와 활동 화면을 함께 바꾸고, 다음 활동에 필요한 UI를 제공한다.
- ‘유지하기’를 선택하면 현재 역할을 유지한다. 이후 다른 역할의 활동을 직접 열면 해당 역할로 전환한다.
- 전환 패널이 나타났다는 이유만으로 역할을 먼저 변경하지 않는다.

**확인 기준:** 유지 선택 시 역할이 유지되고, 전환 선택 시 다음 활동의 정보·기능·역할 표시가 일치한다.

### F-07. AI 개입 및 활동 기억

**목적:** 사용자의 판단이 필요한 변화와 AI 제안을 알아볼 수 있게 전달한다.

- 전체 기획의 개입 상황은 승인 요청·일정 변동·마감 위험·협업 요청·AI 작업 완료다.
- 첫 UT에서는 날씨 변화(강변 촬영의 비 알림)와 협업 문의(러닝 크루원 문의)를 구현한다. 두 상황 모두 해당 활동에 진입했을 때 발생한다.
- 활동 화면에서는 AI 아이콘의 움직임으로 신호를 보내고, 선택 시 상황과 제안을 보여준다.
- 홈에서는 화면 목적에 맞는 문구·캡슐·작업 상태로 표시한다.
- 알림을 열면 읽음 상태로 변경한다.
- 사용자가 전달한 조건은 해당 활동의 기억으로 저장하고, 이후 같은 활동의 브리핑과 제안에 반영한다. 표현이 달라도 같은 의미이면 같은 조건으로 처리하며, 같은 의미인지는 준비 데이터의 별칭 키워드로 판단한다.
- 활동 기억은 확인·수정할 수 있고 마지막 수정 시각을 표시한다.
- 특정 활동의 조건을 다른 활동의 제안에 섞지 않는다.
- 활동 기억 수정만으로 이미 수락한 일정을 자동 변경하지 않는다.

**확인 기준:** 개입 이유와 선택지를 확인할 수 있고, 저장한 조건은 연결된 활동에서만 사용된다. 조건은 텍스트로 입력하며 음성 입력은 제공하지 않는다.

### F-08. AI 대화와 일정 조정

**목적:** 사용자의 조건과 기존 일정을 고려한 대안을 검토한다.

- 대화에서 사용자의 조건을 확인하고 일정·마감·상황을 고려한 조정안을 제시한다.
- 기존 일정과 겹치는 시간을 확정적으로 ‘가능한 시간’이라고 안내하지 않는다.
- 변경 전후 일정과 제안 근거를 함께 보여준다.
- 수락한 경우에만 일정 시각을 변경하고 완료 상태를 안내한다.
- 제안에는 `수락`과 `나중에` 두 버튼만 둔다. `나중에`를 선택하면 기존 일정 시각을 유지하고 제안 상태를 `dismissed`로 바꾼다. 알림을 다시 열면 같은 제안을 다시 보여준다.
- 수락한 제안은 버튼을 완료 상태로 바꾸고 다시 실행할 수 없게 한다.
- 첫 UT에서는 준비된 조건·데이터에 따른 대안을 제공한다. 실제 패턴 분석 기능은 구현 범위로 확정하지 않는다.
- **첫 UT 예외 · 강변 유지 분기(화면만).** Task 6 강변 촬영에서 참가자가 강변 유지를 고르면 일정 조정 대화 → 교체 제안 → 완료 화면을 보여줄 수 있다. 이 화면들은 일정 데이터를 바꾸지 않는다. 교체 제안의 ‘오늘’ 일정에는 브리핑에서 정한 촬영 시각을, ‘내일’은 가상 날짜(11월 14일) 다음 날을 쓴다. 완료 화면 뒤에는 촬영 흐름을 마쳐 오늘 일정에서 완료로 처리하고, 스케줄은 바뀌지 않는다. 그래서 첫 UT에서는 아래 확인 기준 중 ‘수락 후 관련 화면에 같은 변경 결과 표시’를 적용하지 않는다.

**확인 기준:** 수락 전 일정은 유지되고, 수락 후에는 관련 화면에 동일한 변경 결과가 표시된다(첫 UT의 강변 유지 분기는 위 예외).

### F-09. 협업 문의 대응

**목적:** 여러 사람의 공통 요청을 파악하고 대응한다.

- 공통 문의를 요약해 보여준다.
- 사람들이 보낸 문의와 AI의 판단을 출처가 다른 정보로 구분한다.
- 대체 코스 두 후보의 경로·거리·예상 시간을 비교할 수 있게 한다.
- 선택한 코스를 저장하고 공지 초안에 반영한다.
- 공지 초안을 확인한 뒤 발송 버튼을 눌러 모의 발송한다.
- 발송 전 초안과 발송 완료 상태를 구분한다.

**확인 기준:** 선택한 후보와 공지 내용이 일치하며, 발송 전에는 완료로 표시하지 않는다.

### F-10. 러닝 측정 및 백그라운드 AI 작업

**목적:** 현재 활동을 유지하면서 다른 활동의 업무를 맡기고 결과를 확인한다.

- 러닝 측정 전·측정 중·일시 정지 상태를 구분한다.
- 측정 시작 시 경과 시간과 기록이 변하고, 일시 정지 시 숫자 변화가 멈춘다.
- 페이스·심박수는 시간처럼 단순 누적 증가시키지 않는다. 첫 UT의 기록은 모의 값이다.
- 러닝 중 촬영 레퍼런스 검색 등을 요청할 수 있다.
- 요청한 AI 작업은 대상 활동에 연결하되 현재 역할은 유지한다.
- AI 작업은 대기·실행 중·완료로 관리하며 완료 전에는 결과 자료를 공개하지 않는다.
- 첫 UT에서는 Task 8 이후 러닝을 시작한 상태에서 참가자가 채팅을 직접 열어 요청한다(Task 9). 러닝이 브리핑의 몇 번째에 있든 Task 8 → Task 9가 이어진다.
- 첫 UT의 Task 9는 `queued → running → completed`로 진행한다. 요청 직후에는 실행 중이며, 접수만으로 완료하지 않는다. 러닝 화면의 작업 토스트가 완료 문구로 바뀌는 시점(요청·채팅 종료 후 약 5초)에 `job-shoot-extra`를 `completed`로 맞춘다. 완료된 작업의 결과 자료는 기존 공개 규칙을 따른다. 러닝 일정은 러닝 흐름을 마치면 완료된다.
- 결과는 기존 자료와 구분하여 보여준다. 결과 확인만으로 역할을 자동 전환하지 않는다.
- 러닝 화면과 홈에서는 결과 카드(제목·자료 개수)만 보여준다. `촬영 활동에서 보기`를 선택해야 해당 활동으로 진입하며 역할이 바뀐다. 이 경계는 화면 담당자가 구현하며 조정할 수 있다.
- 공지 발송과 AI 작업 요청은 한 번 실행하면 버튼을 완료 상태로 바꾸고 다시 실행할 수 없게 한다.

**확인 기준:** 작업 대상 활동과 현재 역할이 구분되며, 완료 결과가 올바른 활동에 연결된다.

### F-11. 스케줄과 리포트

**목적:** 전체 일정과 활동 결과를 확인한다.

- 스케줄은 오늘·내일의 시각, 활동, 역할, 대기·진행 중·완료 상태를 보여준다.
- 브리핑에서 바꾼 순서를 반영하고, 시간순이 아닌 경우 사용자 지정 순서임을 알린다.
- 수락한 일정 변경은 스케줄에 반영한다.
- 첫 UT 종료 시 스케줄은 `진행 완료`(마친 01~03), `진행 중 / 백그라운드`(진행 중 활동과 아직 끝나지 않은 AI 작업을 구분), `진행 후`(구독 연장·팀플회의, 미완료)로 보여준다. Task 9가 완료된 뒤에는 해당 AI 작업을 실행 중 백그라운드로 두지 않는다.
- 오늘 리포트에서는 활동별 소요 시간, 오래 걸린 활동, 반복 패턴과 피드백을 제공한다.
- 리포트 활동은 세션의 일정과 연결하며, 소요 시간과 과거 패턴에는 가상 데이터를 사용한다.
- 도움이 된 항목을 선택하고 피드백을 입력·저장할 수 있게 한다.
- AI 내부 처리 과정을 모두 나열하기보다 개입 결과와 사용자에게 의미 있는 변화를 보여준다.
- 피드백에 따른 실제 AI 고도화는 첫 UT 검증 범위에 포함하지 않는다.
- 주간 리포트는 주간 패턴, 시즌 리포트는 활동 기간별 반복 패턴과 다음 기간의 피드백을 다룬다. 상세 구현은 첫 UT에서 제외한다.

**확인 기준:** 일정 변경·진행 상태와 리포트의 활동 연결이 일치하고, 피드백 저장 여부를 확인할 수 있다.

| 자료 | 연결 활동, 기존 자료 또는 AI 작업 결과 여부 |
| 활동 기억 | 연결 활동, 조건, 마지막 수정 시각 |
| AI 작업 | 대상 활동, 요청 내용, 실행 상태, 완료 결과 |
| 알림 | 관련 상황, 읽음 여부 |
| 일정 제안 | 변경 전후 내용, 제안·수락 상태 |
| 코스·공지 | 선택한 코스, 초안·모의 발송 상태 |
| 사용자 설정 | 위임 수준, 알림 유형·토글 선택값 |
| 리포트 피드백 | 활동 연결, 입력 내용, 작성 시각 |

이는 개념적 데이터 요구사항이며 DB 스키마나 API 명세를 확정한 표가 아니다. 피드백에서 선택한 항목의 식별값은 리포트 담당과 데이터 담당이 초기 데이터를 만들며 정한다.

### 6.2 상태 변경 규칙

| 사건 | 변경할 상태 | 함께 변경하지 않을 상태 |
|---|---|---|
| 브리핑 순서 변경 | 표시 순서, 01~03 활동의 일정 시각(자리의 시각을 따름) | 04·05의 순서와 시각 |
| 일정 제안 수락 | 대상 일정 시각, 제안 상태 | 다른 활동의 기억 |
| 전환 제안 유지 | 현재 역할 유지 | 다음 역할로의 전환 |
| 다른 역할 활동 진입 | 현재 역할·열린 활동 | 자료·활동 기억의 삭제 |
| 알림 열기 | 읽음 여부 | 제안 수락·공지 발송 여부 |
| AI 작업 완료 | 작업 상태·결과 공개 | 현재 역할의 자동 전환 |
| 공지 발송 선택 | 모의 발송 상태 | 실제 외부 메시지 전송 |
| 활동 기억 수정 | 해당 활동 조건·수정 시각 | 이미 수락한 일정 |
| 오늘 일정의 활동 카드가 홈에 뜨거나 활동 화면이 뜸 | 해당 일정 `in_progress` | 다른 일정의 상태 |
| 해당 활동의 UT 흐름을 마침 | 해당 일정 `done`, 전환 패널 표시 | 현재 역할(참가자가 전환을 선택하기 전까지), AI 작업 상태 |
| AI 작업 요청 접수 | 작업 `queued` → `running` | 작업 `completed`, 현재 역할 |
| 오늘 일정을 다른 날로 옮기는 제안 수락 (첫 UT에는 없음) | 오늘 기준 `done`, 옮긴 날짜에서는 진행 전 | 해당 활동의 자료·기억 |

**일정 상태는 항상 '오늘'을 기준으로 판단한다.**

| 상태 | 의미 |
|---|---|
| 진행 전 `waiting` | 오늘 일정이지만 아직 홈의 활동 카드나 활동 화면으로 보인 적이 없음 |
| 진행 중 `in_progress` | 오늘 일정의 활동 카드가 홈에 뜨거나 활동 화면이 뜬 순간부터 |
| 완료 `done` | 진행 중이 끝남. 해당 활동의 UT 흐름을 마쳤거나, 일정이 오늘에서 다른 날로 옮겨져 더 이상 오늘 일정이 아님 |

- 한 번 진행 중이 된 일정은 다른 화면으로 이동해도 완료되기 전까지 진행 중을 유지한다. 화면을 열거나 전환했다는 이유만으로 일정을 완료 처리하지 않는다.
- 첫 UT에서 리서치는 Task 4, 촬영은 Task 6, 러닝은 Task 8·9의 흐름을 마치면 완료된다. 막힌 경우 진행자가 진행자 패널에서 완료 상태로 옮길 수 있다.
- 구독 연장·팀플회의는 첫 UT에서 진행하지 않으며 종료 시 `진행 후`에 미완료로 남는다.
- 다른 날로 옮긴 일정은 오늘 목록에서 완료와 옮긴 날짜를 함께 표시하고, 옮긴 날짜의 목록에서는 진행 전으로 표시한다.
- 일정 상태와 AI 작업 상태는 별도로 관리한다. 추가 조사 작업은 일정 완료와 자동으로 연동하지 않는다.

## 7. UI 및 인터랙션 요구사항

- 현재 활동을 중심으로 정보 위계를 구성하고, 보조 정보와 AI 작업은 구분한다.
- 역할 태그·활동명·일정 상태·AI 작업 상태를 혼용하지 않는다.
- 네모 형태의 세포와 선을 핵심 시각 언어로 사용한다.
- 역할·활동 전환 패널은 화면 위에서 내려와 작은 반동으로 자리를 잡고, 세포가 선을 따라 이동하며 전환을 안내한다.
- 전환을 선택한 뒤 패널 아래 레이어에서 블루·바이올렛 계열 쉬머가 진행되며 다음 활동 UI를 보여준다. 패널이 올라간 후 쉬머가 약 1.5회 더 진행되는 흐름을 유지한다. 정확한 시간값은 화면 담당자가 정해 코드의 한 곳에 상수로 두고, 바꿀 때도 그곳만 고친다.
- 화면과 Figma 프레임의 대응은 각 화면 담당자가 정한다.
- AI 알림 캡슐은 텍스트 노출과 프레임 확장이 함께 진행된다. 전개 완료 후에는 펼친 상태를 유지한다.
- AI 모션은 독립적인 컴포넌트로 구성하여 배경 화면의 스크롤을 막지 않는다.
- 고정하도록 설계된 상태 바·헤더·하단 내비게이션은 스크롤 중 위치를 유지한다.
- 색상·타이포그래피·간격은 프로젝트의 UI 가이드와 디자인 토큰을 사용한다. 문서에 없는 값을 새 확정값으로 취급하지 않는다.

## 8. 구현 및 UT 운영 기준

### 8.1 구현 기준

- 첫 프로토타입은 휴대폰 화면에서 핵심 경험을 검증하는 용도로 구성한다.
- UI와 데이터 상태를 연결해 같은 일정·자료·작업이 여러 화면에서 일관되게 표시되도록 한다.
- 준비된 데이터와 응답으로 작동하는 부분을 실제 연동·AI 분석 기능과 구분한다.
- 구체적인 UT 인물·시각·대화·모의 수치는 베이스라인의 가상 제안값을 따른다. 가상 날짜는 11월 14일, 한국 시간이다.
- 화면은 React, 코드는 TypeScript, 스타일은 CSS이며 Vite로 실행한다. 첫 UT는 데이터베이스 서버 없이 브라우저에서 가상 데이터를 불러오고, 참가자 변경은 해당 세션에 저장한다. 가상 초기 데이터 `src/fixtures/croxer-ut-baseline.v1.json`과 세션 데이터는 구분한다. 서버와 외부 AI API는 팀이 그 검증을 하기로 한 경우에만 추가한다.

### 8.2 테스트 운영

- 활동 전환은 실제 시간 경과가 아니라 각 활동의 UT 흐름 종료로 발생한다. 비·문의 같은 돌발 상황은 참가자의 순서를 존중해 해당 활동에 진입했을 때 발생한다. 비 예보 알림은 촬영 자료를 연 뒤 기본 10초에 참가자마다 같게 표시하고, 진행자 패널에서도 바로 띄울 수 있게 한다. 시간은 파일럿에서 조정할 수 있다.
- 선행 과제가 막히면 진행자가 진행자 패널에서 다음 활동의 시작 상태로 옮기고 그 개입을 기록한다.
- 참가자 교체 시 초기 데이터를 새로 복사하고, 브리핑 순서·알림·코스 선택·모의 공지·작업 상태를 포함한 세션 상태를 초기화한다.
- 저장은 브라우저에서 한다. 참가자별 기록은 UT 전용 키 하나로 관리할 수 있다. 새로고침해도 참가자 세션 상태는 모두 유지한다.
- 참가자 초기화는 진행자만 진행자 패널에서 실행한다.
- 진행자의 개입은 기록하며, 참가자 개인정보와 실제 세션 기록을 공개 저장소에 포함하지 않는다.

## 9. 검증 관점 및 구현 확인 항목

### 9.1 UT에서 확인할 질문

- 브리핑에서 바꾼 순서대로 활동과 역할 화면이 이어진다고 이해하는가?
- 활동별로 제공되는 정보와 기능을 이해하고 사용할 수 있는가?
- 활동 전환 후 역할·활동·자료의 관계를 파악하는가?
- AI 개입(비 알림, 크루원 문의)의 이유와 제안 내용을 이해하고 다음 행동을 선택하는가?
- 러닝 중 위임한 업무가 접수되어 백그라운드에서 진행 중이라는 것을 이해하는가?
- 스케줄에서 마친 활동, 진행 중인 AI 작업, 남은 활동을 구분하는가?

과제별 성공 기준, 측정 방법, UT 일정은 팀이 UT 운영에서 정하며 이 문서와 구현 범위에 포함하지 않는다.

### 9.2 구현 확인 목록

- [ ] 활동별 정보·기능이 구분되고 관련 자료가 올바른 활동에 연결된다.
- [ ] 01~03의 6가지 순서 모두에서 올바른 역할 화면과 활동 내용이 열린다.
- [ ] 04·05는 드래그하거나 앞 카드로 밀어도 위치가 바뀌지 않는다.
- [ ] 브리핑 순서를 바꾸면 01~03 활동의 시각이 자리를 따라 바뀌고, 04·05의 시각은 그대로다.
- [ ] 전환 유지 선택과 실제 역할 전환이 구분된다.
- [ ] 러닝의 위치와 관계없이 Task 8 → Task 9가 이어진다.
- [ ] AI 작업 요청 뒤 작업은 먼저 실행 중으로 보이고, 정해진 시간(약 5초) 뒤 완료로 표시된다. 화면 문구와 `job-shoot-extra` 상태가 같다.
- [ ] UT 종료 후 스케줄의 진행 완료·진행 중/백그라운드·진행 후가 명세와 같다.
- [ ] 선택한 코스가 공지 초안에 반영된다.
- [ ] 모의 발송과 초안 상태가 구분된다.
- [ ] 러닝 일시 정지 시 기록 변화가 멈춘다.
- [ ] 모션 중에도 필요한 스크롤과 화면 조작이 가능하다.
- [ ] 참가자별 초기화 후 이전 참가자의 상태가 남지 않는다.

## 10. 정책 및 별도 명세

다음 항목은 **첫 UT 범위 밖**이며 구현하지 않는다.

- 회원가입·로그인, 연령 제한, 결제·요금, 데이터 보관·삭제, 외부 연동 권한, 운영·보안 정책.
- 네트워크 오류, 권한 거부, AI 응답 실패 등 실제 서비스의 예외 처리.
- 성능·접근성의 정량 기준.

첫 UT에서 허용하는 입력·분기와 취소·재진입 동작은 11장의 결정 사항을 따른다.

## 11. 결정 사항과 남은 미정 사항

### 11.1 결정 사항 (2026-11-14 팀 결정)

| 구분 | 결정 |
|---|---|
| 구현 범위 | 간단 UT. 브리핑 → 활동 흐름(Task 4·6·8·9) → 스케줄과 이를 잇는 홈·전환 패널·진행자 패널만 만든다(3.1). 영역별 완성 단계(완성·단순하게)는 [협업 가이드](collaboration-guide.md#구현-범위와-완성-단계)에서 관리하고 담당자가 작업하며 조정한다 |
| 활동 순서 | 01~03(리서치·촬영·러닝)만 순서 변경, 04·05(구독 연장·팀플회의)는 고정. 확정한 순서가 활동 진입 순서. 상세는 [간단 UT 활동 순서와 구현 범위](ut-activity-flow.md) |
| Task 번호 | 간단 UT 명세의 번호(Task 4 리서치, 6 촬영, 8 러닝 문의, 9 러닝 중 요청)를 모든 문서의 기준으로 쓴다 |
| 활동 이동 | 한 활동의 UT 흐름을 마치면 완료 처리하고 전환 패널이 다음 순서의 활동을 안내한다. 참가자가 전환·유지를 선택한다 |
| 돌발 상황 | 비 알림·크루원 문의는 해당 활동에 진입했을 때 발생한다 |
| Task 9 연결 | 러닝의 위치와 관계없이 Task 8 → Task 9가 이어진다. 요청 접수만으로 완료하지 않으며, 실행 중을 거친 뒤 완료(`job-shoot-extra` completed)로 맞춘다 |
| 일정 교체 | 일정 시각을 실제로 바꾸는 교체는 첫 UT에서 제외한다. 일정 시각은 브리핑 순서 변경으로만 바뀐다. 예외로 Task 6 강변 유지 분기에서는 일정 조정·교체 화면을 보여주되 데이터는 바꾸지 않는다(F-08, 2026-11-21) |
| 제외 화면 | 회의 녹음 화면과 구독 화면은 만들지 않는다. 두 활동은 브리핑·스케줄 목록에 남은 활동으로만 표시한다 |
| 제외 기능 | 셋업(역할 등록·설정), 활동 기억, 일정 시각을 바꾸는 일정 조정 제안(강변 유지 분기 화면은 예외), AI 작업 결과의 홈·상세 UX 확장(Task 9 완료·자료 공개는 포함, 촬영 자료 ‘AI 정리’ 구분 표시 등은 후속), 리포트(3.2) |
| 입력 방식 | 텍스트만 사용한다. 음성 입력은 제외한다 |
| 같은 의미 판단 | 채팅 입력이 준비 데이터의 별칭 키워드와 맞으면 준비된 응답으로 연결한다. 맞지 않으면 준비된 선택지를 보여준다 |
| 저장 | 새로고침해도 참가자 세션 상태를 모두 유지한다. 초기화는 진행자만 진행자 패널에서 실행한다 |
| 중복 실행 | 공지 발송·작업 요청은 한 번 실행하면 버튼을 완료 상태로 바꾸고 다시 실행할 수 없게 한다 |
| 비 예보 알림 | 촬영 자료를 연 뒤 기본 10초에 표시하고, 진행자 패널에서도 바로 띄운다 |
| 모션 시간 | 화면 담당자가 정해 코드의 한 곳에 상수로 둔다 |
| Figma 대응 | 각 화면 담당자가 정한다 |
| UT 일정·평가 | 팀이 UT 운영에서 정하며 구현 범위에 포함하지 않는다 |
| 정책·예외 처리 | 10장의 항목은 첫 UT 범위 밖이다 |
| 데이터 접근 | 모든 화면은 데이터 담당의 저장·조회 함수로만 데이터를 읽고 쓴다. 세부 규칙은 [개발 가이드](dev-guide.md) |
| ID·상태 값 | [UT 데이터 베이스라인](ut-data-baseline.md)의 ID와 상태 값을 그대로 쓴다. 없는 ID는 UT 담당이 추가한다 |
| 일정 상태 | 항상 오늘 기준. 홈에 활동 카드가 뜨거나 활동 화면이 뜨면 진행 중, 해당 활동의 UT 흐름을 마치면 완료. 6.2 참고 |
| 종료 상태 | 스케줄 `진행 완료`에 01~03, `진행 후`에 구독 연장·팀플회의(미완료), 진행 중 활동과 AI 백그라운드 실행을 구분해 표시 |
| 진행자 패널 | 참가자 초기화, 돌발 상황(비 알림·크루원 문의) 수동 발생, 막힌 과제를 다음 활동의 시작 상태로 이동 |

범위에서 빠진 기능(셋업, 일정 조정 제안, AI 결과 홈·상세 UX 확장)을 이후 구현할 때는 다음 결정을 따른다: 필수 입력은 역할 이름과 활동 이름, 변경은 `저장`을 눌렀을 때만 반영, 제안 버튼은 `수락`·`나중에`, 홈 결과 카드는 `촬영 활동에서 보기`를 선택해야 활동이 바뀜, 촬영 자료에서 AI 결과 묶음 구분 표시(「AI 정리」 등)는 후속, 설정 상세 규칙은 별도로 정함.

### 11.2 담당자가 정할 사항

| 항목 | 정하는 사람 |
|---|---|
| 공용 데이터 폴더 위치, 저장·조회 함수 이름 | 데이터 담당이 정해 [개발 가이드](dev-guide.md)에 적는다 |
| ID 확정, 구독 연장·팀플회의의 표시 시각, 별칭 키워드 목록 | UT 담당이 초기 데이터를 만들며 정한다 |
| 각 활동의 흐름이 끝나는 화면 동작(예: 검토 완료 버튼) | 해당 활동 화면 담당자가 정한다 |
| Task 9 요청 문구와 AI 응답. 원본 명세는 “내일 강변 촬영에 쓸 레퍼런스”이나 일정 교체 제외로 촬영은 오늘 일정임 | 화면 담당과 UT 담당이 맞춘다 |

### 11.3 남은 미정 사항

현재 팀 결정이 필요한 미정 사항은 없다. 새로 생기면 이 표에 추가하고, 팀의 결정 없이 구현 기준으로 적용하지 않는다.
