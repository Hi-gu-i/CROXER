# CROXER UT 데이터 베이스라인

**기획·개발 기준** · 2.0부터 [간단 UT 활동 순서와 구현 범위](ut-activity-flow.md)를 따름

이 문서는 가상 하루를 참가자마다 같은 조건에서 재현하기 위한 **시작 데이터, 사건이 발생하는 조건, 과제 후 기대 상태**를 정의한다. 초기 데이터는 개발용 파일 `src/fixtures/croxer-ut-baseline.v1.json`에 있다. 날짜·시간·장소·코스·자료 본문·AI 답변은 가상 제안값이다. 활동 순서와 Task 번호는 [간단 UT 활동 순서와 구현 범위](ut-activity-flow.md)를 따른다.

## 테스트에서 사용할 가상 하루

가상 날짜는 11월 14일, 시간대는 한국 시간이다. 역할 3개와 활동 5개는 처음부터 등록된 상태로 시작하며, 참가자는 **브리핑**에서 UT를 시작한다. 브리핑의 번호와 시각은 자리에 고정되어 있다. 순서를 바꾸면 그 자리에 온 활동이 자리의 시각(01 13:00, 02 16:00, 03 19:00)을 가지며, 04·05는 21:00·22:00 그대로다. 브리핑을 확정한 뒤 UT 중 일정 시각은 바뀌지 않는다. Task 6 강변 유지 분기에서 보여주는 일정 교체 화면도 일정 데이터는 바꾸지 않는다.

| 초기 순번 | 역할 | 활동 | 테스트 시작 시 준비된 정보 | UT 중 바뀌는 정보 |
| --- | --- | --- | --- | --- |
| 01 | 교양 3조 팀장 | 지역 활성화 사례 리서치 검토 | 오늘 13:00, 어제 밤 정리한 자료(`활성화 사례` 등) | Task 4 흐름을 마치면 완료 |
| 02 | 편집자 | 강변 촬영 | 오늘 16:00, 촬영 참고 자료 | 진입 후 비 알림 → 대안 확인·대화. 흐름을 마치면 완료 |
| 03 | 러닝 크루장 | 한강 러닝 | 오늘 19:00, 기존 강변 흙길 코스 | 진입 시 크루원 문의 → 대체 코스 선택 → 모의 공지 → 러닝 시작 → Task 9 요청. 흐름을 마치면 완료 |
| 04 | 교양 3조 팀장 | ChatGPT 구독 연장하기 | 오늘 21:00. 남은 활동. 별도 화면 없음 | 변화 없음. 종료 시 `진행 후`·미완료 |
| 05 | 교양 3조 팀장 | 팀플회의 / 교양 팀장 녹음 | 오늘 22:00. 남은 활동. 별도 화면 없음 | 변화 없음. 종료 시 `진행 후`·미완료 |

04·05의 표시 시각은 러닝(19:00) 뒤인 21:00·22:00으로 정했다(2026-11-15, UT 담당). UT 종료 시 두 활동은 `진행 후`에 남는다. 초기 데이터의 `startsAt`은 초기 순서 기준 각 자리의 시각이다.

**문구와 시각.** 01~03은 어느 자리로든 갈 수 있으므로 자료·알림·문의·공지·AI 답변 문구에 01~03 활동의 구체적인 시각이나 오전·오후 같은 때를 쓰지 않는다. 날씨는 ‘오늘 하루 종일 비가 오락가락’으로 두어, 러닝이 촬영보다 먼저 오든 나중에 오든 비 알림과 크루원 문의가 함께 성립하게 한다.

| 일정 `Schedule` | `id`, `activityId`, `startsAt`, `status`. 상태는 `waiting` / `in_progress` / `done`이며 오늘 기준으로 판단(PRD 6.2). 홈에 활동 카드가 뜨거나 활동 화면이 뜨면 `in_progress`, 해당 활동의 UT 흐름을 마치면 `done` |
| 브리핑 순서 `briefingOrder` | 일정 ID 목록. 앞 세 칸(리서치·촬영·러닝)만 참가자가 바꿀 수 있고, 뒤 두 칸(구독 연장·팀플회의)은 고정해 합친다. 이 순서가 활동 진입 순서가 됨 |
| 자료 `Resource` | `id`, `activityId`, `title`, `kind`, `body`. AI 작업 결과는 작업 완료 전에는 참가자 화면에서 숨김 |
| AI 작업 `AiJob` | `id`, `activityId`, `title`, `status`, `resultResourceIds`. 상태는 `queued` / `running` / `completed`. 일정 상태와 별개. 요청 접수만으로 `completed`가 되지 않음 |
| 알림 | `id`, `activityId`, `kind`, `status`(`unread` / `read`). 알림을 열면 `read` |
| 문의·코스·공지 | 문의와 AI 판단은 출처가 다른 두 항목. 대체 코스 2개 중 선택값은 `selectedCourseId`. 공지는 `activityId`, `courseId`, `meetingPoint`, `status`(`draft` / `simulated_sent`). 발송 버튼을 눌렀을 때만 상태 변경 |

위 표는 주요 필드다. 초기 데이터 파일의 전체 모양은 `src/data/types.ts`의 `UtBaseline` 타입을 따른다. 타입에는 화면 연결에 필요한 필드(자료의 `aiJobId`, AI 작업의 `requestedInActivityId`, 알림의 `title`·`body`, 문의·AI 판단·코스·공지·별칭 키워드의 구성)가 함께 정의되어 있다.

`activeRoleId`와 현재 열린 활동은 세션 상태다. 역할을 유지하거나 이동해도 저장한 상태를 보존한다. 참가자 교체 시에는 초기 JSON을 새로 복사하고 순서·알림·코스 선택·공지·작업 상태를 모두 초기화한다. 브라우저 저장은 UT 전용 키 하나로 관리하고, 새로고침해도 세션 상태를 모두 유지한다. 초기화는 진행자만 진행자 패널에서 실행한다.

세션에는 `startedAt`(세션을 만든 시각. 새 참가자로 초기화할 때마다 새로 찍음)과 `updatedAt`(마지막으로 바뀐 시각)을 둔다. 참가자와 진행자가 서로 다른 기기를 쓰면 주소의 `?room=방번호`로 같은 세션을 맞춘다. 방 연결 방법은 [개발 가이드](dev-guide.md)의 '방 연결'에 있다.

## 과제별 시작 조건과 기대 결과

‘기대 결과’는 앱이 저장하거나 화면에 보여줘야 하는 값이다. 과제별 성공 기준과 기록 방법은 팀이 UT 운영에서 정하며 구현 범위에 포함하지 않는다.

| 과제 | 시작 조건 | 기대 결과와 확인할 값 |
| --- | --- | --- |
| 브리핑 | 초기 순서 `리서치 검토 → 강변 촬영 → 한강 러닝 → 구독 연장 → 팀플회의` | 01~03은 6가지 중 **어떤 순서든** 저장. 04·05는 이동 핸들이 없고 다른 카드로 밀어도 위치 고정. 번호·시각은 자리에 고정되고 그 자리에 온 활동이 자리의 시각을 가짐(04·05는 21:00·22:00 그대로). 확정하면 첫 번째 활동으로 진입 |
| Task 4 | 리서치 검토 순서 도달. 역할 교양 3조 팀장 | 어제 밤 정리한 자료 열기 → 본문 표시 → 같은 자료 목록으로 복귀 → 검토 마침. 흐름을 마치면 `schedule-research`가 `done` |
| Task 6 | 강변 촬영 순서 도달. 역할 편집자 | 촬영 자료 진입 후 기본 10초에 비 알림. 알림을 열면 `read`. 실내 대안 확인과 AI 대화. 세부 분기는 준비된 화면으로 연결. 강변 유지를 고르면 일정 조정 대화 → 교체 제안 → 완료 화면(화면만, 일정 데이터는 그대로). 어느 분기든 흐름을 마치면 `schedule-shoot`이 오늘 일정에서 `done`. 브리핑에서 정해진 시각은 바뀌지 않음 |
| Task 8 | 한강 러닝 진입. 역할 러닝 크루장 | 진입 시 크루원 문의 발생. 문의와 AI 판단을 출처가 다른 정보로 표시. 대체 코스 2개 중 선택값을 `selectedCourseId`에 저장. 공지 초안은 `draft`, 발송 버튼 뒤 `simulated_sent`. 공지는 선택한 코스와 집결지를 그대로 반영 |
| Task 9 | Task 8 이후 러닝을 시작한 상태에서 참가자가 채팅을 직접 열 때 | 레퍼런스 정리 요청을 `job-shoot-extra`로 등록하고 `activity-shoot`에 연결. 작업 상태 `queued → running → completed`. 러닝 역할 유지. 요청 접수만으로 `completed` 처리하지 않으며, 러닝 토스트가 완료 문구로 바뀌는 시점(약 5초)에 `completed`로 맞춤. 완료 시 결과 자료(`resource-shoot-extra`)는 기존 공개 규칙을 따름. 러닝 흐름을 마치면 `schedule-run`이 `done` |
| 활동 전환 | 한 활동의 흐름을 마침 | 역할 전환 패널이 브리핑 순서상 다음 활동을 안내. 전환을 선택하면 역할 표시와 활동 화면이 함께 바뀜. 유지를 선택하면 현재 역할 유지 |
| UT 종료 | 01~03의 흐름을 모두 마침 | 스케줄 `진행 완료`에 01~03, `진행 후`에 구독 연장·팀플회의(미완료)만 표시. 진행 중 활동과 아직 끝나지 않은 AI 작업을 구분. Task 9를 마친 뒤 `job-shoot-extra`는 `completed` |

## 고정할 사건과 운영 규칙

- **돌발 상황은 진입 시 발생.** 참가자의 순서를 존중하기 위해 비 알림과 러닝 문의는 해당 활동에 진입했을 때 발생한다. 비 알림은 촬영 자료 진입 후 기본 10초이며 파일럿에서 조정할 수 있다. 진행자 패널에서도 같은 사건을 바로 발생시킬 수 있다.
- **Task 9는 러닝 흐름에 붙는다.** 러닝이 몇 번째에 있든 Task 8 → Task 9가 이어지고, 그 뒤 다음 순서의 활동으로 넘어간다.
- **선행 과제가 막혔을 때.** 진행자가 진행자 패널에서 다음 활동의 시작 상태로 옮기고 개입을 기록한다.
- **남은 활동.** 구독 연장과 팀플회의는 브리핑과 스케줄 목록에만 보이며 별도 화면이 없다. 실제 결제·회의 녹음·외부 연동은 구현하지 않는다.
- **텍스트 입력과 별칭 키워드.** Task 6 대화와 Task 9 요청은 텍스트로 입력한다. 초기 JSON에 별칭 키워드 목록을 두고, 입력이 키워드와 맞으면 준비된 응답으로 연결한다. 맞는 키워드가 없으면 준비된 선택지를 보여준다. 키워드 목록은 UT 담당이 관리한다. 키워드는 목록 순서대로 비교해 먼저 맞는 응답을 쓰므로, ‘실내 말고 강변에서’처럼 두 의도가 섞인 입력을 위해 Task 6은 강변 유지 응답을 실내 대안보다 앞에 둔다.
- **확인 필요 · Task 9 문구.** 원본 명세의 요청 내용은 “내일 강변 촬영에 쓸 레퍼런스”다. 일정 교체를 넣지 않기로 해 강변 촬영은 오늘 일정이므로, 초기 데이터에는 러닝이 촬영 앞뒤 어디에 있어도 맞도록 날짜 없이 ‘강변 촬영 편집 레퍼런스 정리’로 넣었다. 화면 담당이 확인한다.

## 파일럿 전에 볼 것

1. 01~03의 6가지 순서 모두에서 올바른 역할 화면과 활동 내용이 열린다.
2. 구독 연장·팀플회의를 드래그하거나 앞 카드로 밀어도 위치가 바뀌지 않는다.
3. 순서를 바꾸면 01~03 활동의 시각이 자리를 따라 바뀌고, 04·05의 시각은 그대로다. 어느 순서에서도 화면 문구가 카드의 시각과 어긋나지 않는다.
4. 러닝의 위치와 관계없이 Task 8 → Task 9가 이어진다.
5. Task 9 요청 뒤 AI 작업은 먼저 실행 중으로 보이고, 정해진 시간(약 5초) 뒤 완료로 표시된다. 화면 문구와 `job-shoot-extra` 상태가 같다.
6. UT 종료 후 스케줄의 `진행 완료`와 `진행 후`가 위 기대 결과와 같다.
7. 초기화 후 새 참가자에게 이전 참가자의 순서, 알림, 코스 선택, 발송 상태, 작업 상태가 보이지 않는다.
