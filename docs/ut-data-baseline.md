# CROXER UT 데이터 베이스라인

**기획·개발 검토안** · 팀의 `Take Scneario` 이미지 5장 기준

이 문서는 지호의 가상 하루를 참가자마다 같은 조건에서 재현하기 위한 **시작 데이터, 사건이 발생하는 조건, 과제 후 기대 상태**를 정의한다. 초기 데이터는 별도의 개발용 파일 `croxer-ut-baseline.v1.json`으로 준비했다. 날짜·시간·장소·코스·자료 본문·AI 답변은 이 문서에서 채운 가상 제안값이다. 팀 시나리오에 나온 과제 번호와 역할은 그대로 참조했다.

## 테스트에서 사용할 가상 하루

가상 날짜는 11월 14일, 시간대는 한국 시간이다. 참가자가 브리핑에서 순서를 바꿔도 실제 일정 시각은 그대로 표시한다. 일정 시각은 Task 7-2의 변경 수락 때 바뀐다.

| 역할 | 활동 | 테스트 시작 시 준비된 정보 | UT 중 바뀌는 정보 |
| --- | --- | --- | --- |
| 학생 · 교양 3조 팀장 | 지역 활성화 팀 프로젝트 | 오늘 13:00 회의, `활성화 사례` 자료, 추가 사례 정리 진행 중 | 역할과 활동은 참가자가 등록한다. 회의 구간 뒤 일정 완료 처리 |
| 여행 콘텐츠 제작자 · 편집자 | 강변 촬영 | 오늘 16:00 촬영, 기존 참고 자료 1개 | 비 예보와 강변 촬영 조건 입력 후 내일 16:00로 이동. 러닝 뒤 추가 레퍼런스 공개 |
| 여행 콘텐츠 제작자 · 편집자 | 촬영 자료 정리 | 내일 16:00 자료 정리 | 일정 교체 시 오늘 16:00로 이동. 하루 마감 시점에도 진행 중인 활동으로 사용 |
| 러닝 크루장 | 저녁 크루 러닝 | 오늘 19:00 러닝, 기존 강변 흙길 코스 | 문의 도착 → 대체 코스 선택 → 모의 공지 발송 → 러닝 완료 |

**Task 0과 Task 1의 시작 상태를 구분한다.** Task 0은 지호의 읽기 전용 홈 미리보기로 탐색한다. Task 1은 등록한 역할과 활동이 비어 있는 셋업에서 시작한다. JSON에 있는 지호의 역할 목록은 정답과 예시 연결용이며, 처음부터 가입이 완료된 상태를 뜻하지 않는다. Task 1-1에서 팀 프로젝트를 등록하면 준비된 일정·자료를 같은 활동 ID에 연결한다. 촬영·러닝·자료 정리는 역할 등록 후 제공되는 예시 활동으로 설정한다.

## 개발팀이 공유할 이름과 상태

| 데이터 | 주요 필드와 규칙 |
| --- | --- |
| 역할 `Role` | `id`, `name`, `label`. 화면 문구가 바뀌어도 ID는 유지. `학생`은 역할이며 `지역 활성화 팀 프로젝트`는 그 역할의 활동 |
| 활동 `Activity` | `id`, `roleId`, `name`, `source`. 하나의 역할은 여러 활동을 가질 수 있음 |
| 일정 `Schedule` | `id`, `activityId`, `startsAt`, `endsAt`, `status`. 상태는 `waiting` / `in_progress` / `done`. 브리핑 표시 순서는 `briefingOrder`에 일정 ID 목록으로 저장 |
| 자료 `Resource` | `id`, `activityId`, `title`, `kind`, `body`. 대기 중인 작업 결과는 카탈로그에 있어도 완료 전에는 참가자 화면에서 숨김 |
| 활동 기억 `ActivityMemory` | `activityId`, `condition`, `source`, `updatedAt`. Task 7-1에서 `activity-shoot`에만 강변 촬영 조건을 기록. 날짜와 코스 제안을 만들 때는 해당 활동의 조건만 조회 |
| AI 작업 `AiJob` | `id`, `activityId`, `title`, `status`, `resultResourceIds`. 상태는 `queued` / `running` / `completed`. 일정의 진행 상태와 별개 |
| 알림·제안 | 알림 `id`, `activityId`, `kind`, `status`(`unread` / `read`). 일정 제안 `id`, `status`(`offered` / `accepted` / `dismissed`), `changes`. 수락 때만 일정 갱신 |
| 문의·공지 | 문의와 AI 판단은 출처가 다른 두 항목. 공지는 `activityId`, `courseId`, `meetingPoint`, `status`(`draft` / `simulated_sent`). 발송 버튼을 눌렀을 때만 상태 변경 |
| 리포트·피드백 | 리포트의 오늘 활동은 해당 세션 일정과 연결하고, 소요 시간·과거 패턴에는 가상 데이터를 사용. 피드백은 `activityId`, `text`, `createdAt`을 세션에 저장 |

`registeredRoleIds`·`registeredActivityIds`·`activeRoleId`는 세션 상태다. 역할을 유지하거나 이동해도 저장한 일정과 기억을 보존한다. 참가자 교체 시에는 초기 JSON을 새로 복사하고 등록·알림·변경안·작업·모의 공지·피드백을 모두 초기화한다. 프로토타입에서 브라우저 저장으로 구현할 경우 참가자별 기록은 UT 전용 키 하나로 관리할 수 있다.

## 과제별 시작 조건과 기대 결과

‘기대 결과’는 앱이 저장하거나 화면에 보여줘야 하는 값이다. 참가자의 성공 여부는 관찰자가 실제 행동과 발화를 보고 기록한다.

| Task | 참가자에게 제공할 시작 조건 | 기대 결과와 확인할 값 |
| --- | --- | --- |
| 인터뷰 · 탐색 | 서비스 설명, 지호 역할 카드, 읽기 전용 홈 | 실제 참가자의 앱·AI 경험은 관찰 기록에 작성. 탐색 상태는 셋업에 이어지지 않음 |
| 1 · 1-1 | 비어 있는 셋업, 역할 세 가지와 팀 프로젝트 상황 설명 | 역할 3개 등록. 학생 아래 `지역 활성화 팀 프로젝트` 연결. 자연스러운 별칭은 같은 역할로 인정 |
| 2 · 2-1 | 오늘 일정 3개, 초기 표시 순서 `팀 프로젝트 → 강변 촬영 → 러닝` | 참가자가 선택한 **어떤 순서든** 저장. 스케줄 화면에서 변경 순서 확인. 일정의 시간은 유지 |
| 3 · 3-1 · 3-2 | 홈, 당시 일정 대기 상태와 `팀프로젝트 사례 리서치 정리` 작업 진행 중 | 홈에서 볼 수 있는 정보 설명. Task 3-1은 응답 시점에 **홈 맨 위에 보이는 활동**을 말하면 성공. 대기 일정과 실행 중 AI 작업을 각각 식별 |
| 4 · 4-1 · 4-2 | 교양 3조 팀장 맥락, 사례 리서치 영역 | `활성화 사례` 문서 열기 → 본문 표시 → 같은 자료 목록으로 복귀. 기존 사례 열람과 추가 정리 작업은 동시에 가능 |
| 5 · 5-1 | 진행자가 팀 프로젝트 구간 종료 후 전환 발생 | 학생 → 편집자. 역할 이름과 `강변 촬영` 맥락을 말할 수 있는지 확인. 색상·속도 반응은 발화로 기록 |
| 6 · 6-1 | 강변 촬영 자료를 열고 정해진 시점에 비 예보 알림 노출 | 자발적 발견을 먼저 관찰. 알림을 열면 `read`로 변경. 참가자가 비 예보와 대안 검토 제안을 설명 |
| 7 · 7-1 | 비를 피할 실내 장소 1개 제안 | 대안 장소 확인 후 참가자가 강변 촬영 조건 전달. `activity-shoot`에 조건 저장. 표현이 달라도 같은 의미면 처리 |
| 7-2 | 강변 조건 반영 후 두 일정 교체안 표시 | 근거와 두 일정의 이동을 확인하고 수락하면 `schedule-shoot`는 내일 16:00, `schedule-edit`는 오늘 16:00로 이동. 보류·닫기 시 시간 유지 |

| 9 · 9-1 | 크루원 문의와 젖은 흙길에 대한 AI 판단을 별개로 노출 | 출처 구분. 대체 코스 2개 중 선택한 값을 `selectedCourseId`에 저장. 추천 근거 설명을 관찰하며 합리적인 대체 선택을 인정 |
| 9-2 | 선택한 코스, 19:00, 해당 집결지를 사용한 공지 초안 | 발송 전 `draft`. 버튼 선택 뒤 `simulated_sent`. 공지는 선택한 코스와 집결지를 그대로 반영 |
| 10 | 현재 러닝 역할, 내일 16:00 강변 촬영 일정 | 추가 검색 요청을 `job-shoot-extra`로 등록하고 `activity-shoot`에 연결. 작업 상태 `queued → running`. 러닝 역할 유지 |

| 11 | 가상 하루 마감 | 오늘 일정에 완료 `팀 프로젝트·러닝`, 진행 중 `촬영 자료 정리` 표시. 강변 촬영은 내일 일정에 표시. 오늘 대기 일정과 해당 항목의 판정 기준은 팀 논의 후 확정 |

## 고정할 사건과 팀이 정할 선택지

- **Task 2와 3-1.** 사용자가 브리핑에서 맨 위에 올린 활동을 홈에서도 먼저 보여준다. 진행자는 질문 시점에 홈 맨 위에 실제로 보인 활동명과 참가자 답을 기록한다. 이 질문은 홈에서 먼저 할 활동을 알아차렸는지 확인하기 위한 것이다.
- **Task 4.** 화면에 이미 만들어진 `활성화 사례`와 진행 중인 추가 조사 상태를 함께 둔다. Task 5 직전 팀 프로젝트 일정은 완료 처리한다. 추가 조사 작업 상태는 일정 완료에 자동 연동하지 않는다.
- **Task 6.** 파일럿에서 자료 진입 후 몇 초에 알림을 띄울지 정하고 참가자마다 동일하게 적용한다. 먼저 힌트 없이 반응을 관찰한 다음 Task 6-1 질문을 한다. Task 5·8 전환과 Task 10-1 완료도 실제 시간 경과에 맡기기보다 과제 구간에서 진행자가 같은 조건으로 발생시킨다.
- **Task 7-2와 10.** 정상 흐름에서는 오늘 촬영이 내일로 이동하므로 Task 10의 ‘내일 촬영’과 맞는다. 일정 변경을 거절했거나 실패한 참가자는 `7-2 미완료`로 기록하고, Task 10 전 진행자가 **교체 완료 상태로 이동**시켰음을 남긴다. 코스 선택 등 선행 과제가 막혔을 때도 같은 방식으로 진행자 개입을 기록한다.
- **Task 11 · 팀 논의 필요.** 강변 촬영을 내일로 옮기고 러닝을 마치면 현재 데이터에 오늘 대기 일정이 남지 않는다. 과제에서 ‘앞으로 남은 활동’을 계속 확인할지와 그때 보여줄 일정을 팀에서 정한다.
- **Task 12-1.** 첫 테스트에서는 피드백이 저장됐다는 결과를 보여준다. 다음 제안에 실제 반영되는지까지 검증하려면 같은 도움 상황을 다시 띄우는 별도 과제가 필요하다.
- **시나리오 이미지의 붉은 메모.** 초안 범위에는 GPT 구독 화면과 팀 회의 녹음 과제를 넣지 않았고, 러닝 중 배경 작업 요청이 역할을 즉시 바꾸지 않도록 했다. 팀이 이 메모를 확정하면 과제 카드에도 반영한다.

## 파일럿 전에 볼 것

1. 역할이 비어 있는 셋업에서 3개를 등록하고 학생 아래에 프로젝트가 연결되는지 확인한다.
2. 초기 순서를 바꿨을 때 화면 사이에서 유지되고, 일정 시각은 제안 수락 때만 바뀌는지 확인한다.
3. 강변 조건이 러닝에 섞이지 않고, 선택한 코스가 공지의 코스·집결지에 함께 반영되는지 확인한다.
4. 러닝을 끝내기 전에는 추가 레퍼런스가 숨겨지고, 종료 후에는 자료와 완료 상태가 표시되는지 확인한다.
5. 초기화 후 새 참가자에게 이전 참가자의 순서, 입력, 발송 상태, 피드백이 보이지 않는지 확인한다.
