# CROXER AI 협업 요청 가이드

팀원 네 명이 각자 AI와 작업하면서, 다른 팀원 파트가 필요할 때 **요청을 주고받는 방법**을 정한 문서입니다. 보내는 쪽 AI가 요청을 **요청 카드**로 정리하고, 받는 쪽 AI는 그 카드만 보고도 무엇을 왜 해야 하는지 알 수 있게 합니다. 누가 어떤 파일을 맡았는지는 [협업 가이드의 담당 업무와 일정](collaboration-guide.md#담당-업무와-일정)에 있습니다.

## 팀원은 여기만 읽으세요

**요청을 보낼 때**

1. 평소처럼 AI에게 하고 싶은 일을 말합니다. 다른 사람 파트가 필요하면 AI가 먼저 알려주고 **요청 카드**를 만들어 줍니다.
2. AI가 안내하는 대로 GitHub에서 이슈를 만듭니다. 저장소 페이지 → `Issues` → `New issue` → **AI 요청** 선택 → 카드 내용을 붙여 넣기 → 오른쪽 `Assignees`에서 받는 사람 선택 → `Submit new issue`.
3. 급하면 팀 채팅에 이슈 링크와 한 줄 요약을 같이 보냅니다.
4. 기다리는 동안에도 AI는 내 파트에서 할 수 있는 작업을 이어갑니다.

**요청을 받았을 때**

1. 이슈에 있는 카드 전체를 복사해 내 AI에게 붙여 넣고 이렇게 말합니다.

   > 팀원한테 온 요청이야. CROXER AI 협업 요청 가이드에 따라 처리해줘.

2. AI가 할 수 있는지, 바꿔야 할 점이 있는지 먼저 정리해 줍니다. 진행하면 내 작업 브랜치에서 처리하고 **답장 카드**를 만들어 줍니다.
3. 답장 카드를 이슈 댓글로 남깁니다. 변경을 담은 PR이 합쳐지면 이슈를 닫습니다.

**충돌이 났을 때**는 AI에게 “합치는 중에 충돌이 났어”라고 말하세요. 누구와 무엇이 부딪혔는지 **충돌 카드**로 정리해 줍니다. 같은 방법으로 이슈를 만들고, 파일 주인과 통합 담당을 `Assignees`에 넣습니다.

---

## 아래부터는 AI 작업 지침입니다

당신은 코드 경험이 없는 팀원의 작업을 돕는다. 팀원은 서로의 코드를 읽지 않으므로, 다른 팀원에게 보내는 내용은 **받는 사람의 AI가 이 카드 하나만 보고 작업할 수 있도록** 쓴다. 보내는 쪽 대화 내용, 내 컴퓨터에만 있는 변경, “아까 말한 그것” 같은 표현에 기대지 않는다.

### 1. 요청이 필요한지 판단하기

다음 중 하나에 해당하면 직접 수정하지 않고 요청 카드를 만든다.

- 수정해야 할 파일이 [담당 업무와 일정](collaboration-guide.md#담당-업무와-일정)에서 다른 역할의 소유다. 예: 공용 저장·조회 함수, 가상 초기 데이터, 공통 컴포넌트, `src/App.tsx`·`src/index.css`.
- 여러 화면이 같이 쓰는 데이터 필드나 함수 이름을 새로 만들거나 바꿔야 한다.
- 다른 역할이 정할 동작(예: 일정 상태가 바뀌는 시점)을 알아야 결과가 달라진다.
- 합치는 중에 다른 사람의 변경과 충돌했다.

받는 사람은 `이름(역할)` 형식으로 적는다. 예: `예은(① 통합)`. 담당표에 없는 파일이거나 소유가 모호하면 통합 담당에게 보낸다. 내 파일만으로 해결할 수 있으면 요청하지 않는다.

### 2. 요청을 보낼 때

1. 사용자에게 먼저 한두 문장으로 알린다. 어떤 파일이 누구 담당이라 직접 고치지 않는지, 그동안 내 파트에서 무엇을 계속하는지 말한다.
2. 아래 형식으로 요청 카드를 쓴다. **한 카드에는 요청 하나**만 담는다. 받는 사람 기준으로 쉬운 말을 쓰고, 파일명·함수명은 필요한 곳에만 괄호로 덧붙인다.
3. 내가 제안하는 함수 이름이나 데이터 모양은 **제안**으로 표시한다. 최종 결정은 파일 주인이 한다. 기존 이름 규칙은 [개발 가이드](dev-guide.md)와 [UT 데이터 베이스라인](ut-data-baseline.md)을 따른다.
4. 기다리는 동안에는 내 기능 폴더 안에서 임시 값으로 화면을 계속 만든다. 임시 값은 나중에 바꿀 위치를 알 수 있게 표시하고, 다른 사람의 파일에 임시 코드를 넣지 않는다.
5. 카드를 출력한 뒤 사용자에게 **보낼 곳 → 누구에게 → 누를 버튼** 순서로 안내한다. 아래 '사용자에게 보여줄 안내' 형식을 쓴다.
6. 참가자 개인정보, 비밀키, 환경 파일의 실제 값은 카드에 넣지 않는다.

#### 요청 카드 형식

````markdown
## [요청] 받는 사람(역할) ← 보내는 사람(역할): 한 줄 요약

**종류:** 데이터 함수 추가 / 데이터 필드 변경 / 공통 부품 / 화면 연결 / 동작 결정 / 질문 중 하나

**왜 필요한가요?**
사용자가 어떤 화면에서 무엇을 하려는지, 지금 무엇이 막혀 있는지 2~3문장.

**원하는 결과 (완료 조건)**
- 받는 사람이 끝냈을 때 확인할 수 있는 결과를 적습니다.

**관련 기준**
- PRD 기능 번호, UT 과제 번호, 지켜야 할 상태 규칙(PRD 6.2)

**제안하는 모양 (참고용, 최종 결정은 받는 사람)**
- 예: 함수 이름, 받는 값과 돌려주는 값, 컴포넌트에 넘길 값

**지금 내 상태**
- 내 브랜치·PR 링크(올렸다면), 임시 값으로 진행 중인 부분

**필요한 시점:** 날짜 또는 "이 PR을 합치기 전까지"
````

#### 사용자에게 보여줄 안내

카드 바로 아래에 다음을 출력한다.

```text
📮 이 요청은 [받는 사람(역할)] 님에게 보내야 해요.
1. GitHub 저장소 → Issues → New issue → "AI 요청" 선택
2. 위 카드 전체를 붙여 넣고, Assignees에서 [받는 사람]을 선택한 뒤 Submit new issue
3. 급하면 팀 채팅에 이슈 링크와 함께 "[한 줄 요약]"이라고 보내 주세요.
그동안 저는 [내 파트에서 계속할 작업]을 이어갈게요.
```

### 3. 요청을 받았을 때

1. 카드를 읽고 받은 요청을 한 문장으로 다시 말한다. 현재 `main`과 내 파일을 직접 확인한다.
2. 다음 중 하나로 판단해 사용자에게 알린다.
   - **그대로 가능.** 내 작업 브랜치에서 처리한다.
   - **조정 필요.** 제안된 이름이나 모양이 기존 규칙과 다르거나 다른 화면에 영향을 주면, 바꿀 점과 이유를 정리한다.
   - **확인 필요.** 결과가 달라지는 정보가 빠졌으면 보낸 사람에게 물을 질문 **하나**를 만든다.
3. 처리할 때는 [협업 가이드](collaboration-guide.md)의 작업·검증 절차를 따른다. 요청받은 변경만 하고, 다른 화면이 이미 쓰는 이름은 바꾸지 않는다. 바꿔야 하면 영향을 받는 사람을 답장 카드에 적는다.
4. 끝나면 답장 카드를 만들고, 사용자에게 이슈 댓글로 남기도록 안내한다.

#### 답장 카드 형식

````markdown
## [답장] 보낸 사람(역할) → 받는 사람(역할): 한 줄 요약

**결과:** 완료 / 조정해서 완료 / 확인 필요 / 진행 어려움

**바뀐 점**
- 요청과 달라진 부분이 있으면 무엇이 왜 달라졌는지 적습니다.

**사용 방법**
- 요청한 사람의 AI가 바로 쓸 수 있게 함수 이름, 넘길 값, 화면 연결 방법을 적습니다.

**확인 방법**
- 어떤 화면에서 무엇을 누르면 결과를 볼 수 있는지 적습니다.

**PR:** 링크 (합쳐진 뒤 `main`을 받아야 쓸 수 있음)

**영향 받는 사람:** 없으면 "없음"
````

### 4. 충돌이 났을 때

1. 충돌한 파일과 양쪽 변경 내용을 실제로 읽는다. 양쪽의 목적이 모두 살아 있는 해결이 분명하고 그 파일이 내 담당이면, [협업 가이드](collaboration-guide.md) 5번 절차로 직접 해결한다.
2. 상대 담당의 파일이거나 어느 쪽을 살릴지 판단이 필요하면 해결을 멈추고 충돌 카드를 만든다. 상대 변경을 지우거나 덮어쓰는 해결은 하지 않는다.

#### 충돌 카드 형식

````markdown
## [충돌] 파일 주인(역할) · 통합 담당 ← 보내는 사람(역할): 충돌한 파일

**어디서:** 내 브랜치 → 합치려던 대상(보통 main), 관련 PR 링크

**충돌한 파일:** 파일 경로

**내 변경의 목적:** 화면에서 무엇이 달라지려던 것인지

**상대 변경의 목적:** 커밋 메시지·PR 제목에서 확인한 내용. 추정이면 "추정"이라고 적습니다.

**제안하는 해결:** 두 목적을 모두 살리는 방법, 또는 결정이 필요한 질문 하나

**지금 상태:** 합치기를 멈춘 상태인지, 내 변경은 안전하게 커밋되어 있는지
````

### 5. 공통 규칙

- 다른 역할의 파일은 직접 고치지 않는다. 마감이 임박해 예외가 필요하면 파일 주인의 동의를 이슈 댓글로 남긴 뒤 진행한다.
- 카드 제목은 `[요청]`·`[답장]`·`[충돌]`로 시작해 이슈 목록에서 구분되게 한다.
- 요청과 답장은 GitHub 이슈 한 곳에 모은다. 팀 채팅으로 받은 요청도 이슈로 옮겨 기록을 남긴다.
- 담당자나 파일 소유권이 바뀌면 협업 가이드의 담당표를 먼저 고친다.
