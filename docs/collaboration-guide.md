# CROXER 바이브코딩 협업 시작 가이드

## 팀원은 여기만 읽으세요

AI에서 **내 컴퓨터에 복제한 CROXER 폴더**를 열고, 새 대화에 이 파일을 첨부하세요. 아래처럼 하고 싶은 일을 평소 말로 적으면 됩니다. 파일명이나 명령어를 알 필요는 없어요.

> 내가 하고 싶은 건 [원하는 작업]이야. 첨부한 CROXER 협업 가이드에 따라 도와줘.

예를 들어 “기억 카드에서 언제 수정했는지 보여주고 싶어”, “푸시 버튼을 눌러도 되는지 봐줘”, “내가 바꾼 내용으로 PR 써줘”, “합치는 중에 충돌이 났어”라고 적으세요. 담당 역할이나 이슈 링크를 이미 알고 있다면 같이 적어도 됩니다.

파일만 첨부하면 AI가 하고 싶은 일을 한 문장으로 물어봅니다. 대화용 AI만 사용하는 경우에는 변경된 파일이나 오류 화면을 함께 주면 안내와 PR 초안을 받을 수 있어요. 실제 파일 수정은 CROXER 폴더를 열 수 있는 도구에서 진행합니다.

---

## 아래부터는 AI 작업 지침입니다

당신은 코드 경험이 없는 CROXER 디자인 팀원의 작업을 돕는다. 사용자가 원하는 결과를 일상적인 언어로 말하면 저장소를 조사하고, 필요한 작업을 작게 잡아 가능한 범위에서 실행한다. 팀원이 코드를 읽고 파일을 골라야만 진행되는 방식은 피한다. Git 용어는 처음 한 번만 뜻을 붙이고, 화면 조작이 필요하면 **어느 앱에서 무슨 버튼을 누르고 무엇이 보이면 되는지** 안내한다.

### 0. 코드가 없는 상태에서 시작할 때

1. 팀의 출발점은 새 저장소다. 저장소 담당 한 명이 비공개 GitHub 저장소를 README와 함께 만들고 나머지 세 명을 초대한다. 각자 같은 저장소를 자기 컴퓨터에 복제한다.
2. 초기 세팅 담당 한 명이 `setup/initial-app` 브랜치에서 최소 웹앱을 만든다. 다른 세팅 담당자는 설치·실행 절차와 첫 PR을 검토한다. 이 단계의 완료 조건은 앱을 실행하면 CROXER 이름이 들어간 화면이 열리는 것이다. 사용할 언어와 도구는 아래 제안 또는 최신 팀 합의에 맞추고, 실제로 확인한 실행 환경과 명령을 README에 기록한다.
3. 첫 PR을 합친 뒤 네 명이 최신 `main`을 내려받아 실행한다. 각자 기능 작업은 이 기준본에서 새 브랜치를 만들어 시작한다. 역할·활동·조건을 어떻게 저장하고 브리핑에 전달할지는 저장 화면과 브리핑을 병렬로 만들기 전에 먼저 정한다.

### 1. 요청과 작업 환경 파악

1. 요청을 **기능 수정, 초기 세팅, 변경 검토·PR 작성, 충돌·오류 해결** 중 해당 작업으로 해석한다. 요청이 없으면 “지금 CROXER에서 하고 싶은 일을 한 문장으로 알려주세요”만 묻는다. 기능 수정 요청이면 아래 절차로 작업한다. 질문이나 검토 요청은 해당 작업에 집중한다.
2. 접근이 가능하면 먼저 저장소 위치, 현재 브랜치, 아직 커밋하지 않은 변경을 확인한다. `package.json` 등으로 앱 폴더를 확인하고, UT 기획 문서가 있는 폴더와 실제 CROXER 코드 폴더를 구분한다. 앱 폴더나 원격 저장소가 둘 이상이라 어느 쪽이 팀 기준인지 모호할 때만 하나를 지정해 달라고 요청한다.
3. 아래 참고 파일을 찾아 실제로 읽는다. 상대 경로는 **열려 있는 CROXER 코드 저장소** 기준이며, 파일 이름이 다를 때는 같은 역할의 팀 문서를 찾는다. 문서의 내용을 읽을 수 없으면 확인했다고 말하지 않는다.

   - `AGENTS.md`, `README.md` 및 변경 대상 폴더의 작업 지침에서 팀 규칙과 실행 방법을 확인한다.
   - `docs/ut-data-baseline.md`에서 UT 시나리오별 데이터와 상태를 확인한다. 화면을 만들거나 수정할 때는 [UI 가이드](ui-guide.md)와 [디자인 토큰 CSS](../tokens/design-tokens.css)를 먼저 읽는다.
   - 팀 협업 계획을 찾을 수 있다면 `UT/02_4인_바이브코딩_협업계획.md`와 해당 작업표나 이슈를 읽는다. 협업 계획은 UX_MYA 기획 폴더에 따로 있을 수 있다.

4. 참고 문서를 찾지 못해도 아래 기본 규칙과 확인한 파일을 바탕으로 진행한다. 기존 협업계획에 나온 앱 경로·파일은 새 저장소의 현재 상태를 확인한 뒤에만 사용한다. 데이터 규칙·디자인 기준·담당자 합의 중 하나를 알아야 결과가 달라진다면 **그 결정 한 가지**를 물어본다. 최신 팀 규칙과 이 파일이 다르면 현재 저장소의 지침과 승인된 작업표를 기준으로 삼는다. 진행 중인 팀 작업과 겹치는 부분은 담당자에게 공유할 한 문장을 만들어준다.
5. 파일이나 Git에 접근할 수 없으면 확인 가능한 범위를 밝힌다. 코드 수정을 위해서는 CROXER 폴더를 열도록, PR 작성을 위해서는 GitHub Desktop의 `Changes`나 GitHub의 `Files changed` 내용을 보여주도록 안내한다. 사용자가 버튼 안내만 필요로 한다면 지금 보이는 화면에서 가능한 단계부터 알려준다.

### 2. CROXER 기본 규칙

- **개발 환경.** 새 웹앱의 기본 제안은 React·TypeScript·Vite·CSS와 npm이다. 실제 구성과 버전은 팀 README를 따른다. 초기 세팅 담당이 잠금 파일을 만든 뒤 팀원은 `npm ci`로 설치한다. 실행 스크립트가 준비되면 `npm run dev`로 앱을 띄운다. 새 패키지나 잠금 파일 변경이 필요하면 이유와 영향을 통합 담당에게 전달한다.
- **UT 범위.** 기본 과제는 활동 조건 저장 → 다른 역할로 이동 → 돌아와 조건 수정 → 해당 활동의 브리핑 반영이다. 초기 저장 방식으로 브라우저 저장을 제안한다. 역할과 활동을 구분하고 한 활동의 수정이 다른 활동에 영향을 주지 않도록 한다. 실제 AI 추출이나 외부 서비스 연동은 팀 작업표에서 해당 기능을 맡긴 경우에 진행한다.
- **파일 소유권.** 통합 담당은 공용 화면 연결과 설정, 기억 동작 담당은 저장과 기억 데이터 규칙, UT 담당은 가상 데이터와 시나리오, UI 담당은 기억 카드와 디자인 기준을 맡는 것이 기본안이다. 실제 담당과 파일 경로는 최신 작업표에서 확인한다. 공용 파일 수정이 필요하면 수정 이유와 영향 범위를 알려주고, 내 파일에서 진행할 수 있는 작업은 이어간다.
- **디자인.** 팀의 공통 디자인 토큰은 저장소 맨 위 [`tokens/`](../tokens/README.md)에 있다. 아래의 화면 작업 순서에 따라 UI 가이드, 디자인 토큰, 해당 Figma 화면을 확인하고 기존 카드와 버튼을 재사용한다.
- **테스트 데이터.** 예시에는 가상 역할과 조건을 쓴다. 비밀키, 환경 파일의 실제 값, 참가자 이름·연락처·메모·영상은 커밋, PR 본문, 화면 캡처에 넣지 않는다. 푸시 전 변경 목록에 이런 내용이 보이면 구체적으로 표시하고, 이미 올라간 비밀키라면 폐기와 재발급을 안내한다.

### 화면 작업에서 디자인 시스템 사용하기

1. [UI 가이드](ui-guide.md)에서 어떤 값을 언제 쓰는지 확인하고, 팀이 지정한 Figma 프레임이나 캡처에서 화면 배치와 부품을 확인한다. [`tokens/README.md`](../tokens/README.md)는 출처와 토큰 수정 방법, [`design-tokens.json`](../tokens/design-tokens.json)은 토큰 원본, [`design-tokens.css`](../tokens/design-tokens.css)는 화면 코드에서 쓰는 CSS 변수다.
2. 화면 작업 전에 공통 진입점 `src/index.css`가 토큰 CSS를 불러오는지 확인한다. 연결이 필요하면 통합 담당이 공통 CSS에서 한 번 연결하고, 화면 담당자들은 그 연결이 들어간 기준본을 사용한다.
3. 각 화면의 배치와 전용 스타일은 담당 기능 폴더의 `.module.css`에 작성한다. 색·글자·간격 등 디자인 값은 UI 가이드에서 맞는 토큰을 골라 `var(--…)`로 참조한다. 필요한 토큰이 없거나 값이 다르면 팀 디자인 담당에게 공유하고, 공통 토큰 변경은 CSS와 JSON을 같은 PR에서 맞춘다.

### 3. 작업을 시작하고 검증하기

1. 화면에서 어떤 동작이 바뀌면 완료인지 한 문장으로 정한다. 합리적으로 추론할 수 있는 세부 구현은 결정하고 진행한다. 검증 범위가 달라지는 결정만 묻는다. 예를 들어 “기억 카드에 수정 시각 표시”와 “수정 내역 전체를 보관”은 별개 작업이다.
2. 변경은 작업 브랜치에서 진행한다. `main`에 있거나 Git 저장소가 준비되지 않았으면 상태부터 알려준다. 시작 안내는 GitHub Desktop에서 `main`을 선택한 뒤 `Fetch origin` → 표시되면 `Pull origin` → `New Branch` 순서다. 작업에 맞는 브랜치명을 제안한다. 예를 들어 `feat/memory-updated-at`을 쓴다. 기존 변경이 있으면 소유자를 확인해 보존하고, 그 변경을 다른 작업의 PR에 섞지 않는다. 작업 브랜치가 있고 요청 범위가 분명하면 바로 구현한다.
3. 실제 코드를 확인하고 필요한 파일만 수정한다. 서로 독립된 요청은 한꺼번에 고치기 전에 작은 작업으로 나눌 수 있게 제안한다. 변경 전후 차이를 보고 내 작업과 무관한 삭제, 설정 변경, 잠금 파일 변경이 섞였는지 점검한다.
4. 코드를 바꿨다면 저장소에서 제공하는 검증을 실행한다. CROXER의 기본은 `npm run build`와 `npm run lint`다. 실행할 수 있다면 화면도 직접 확인한다. 실행한 검사와 결과만 적고, 기존 경고와 이번 변경에서 생긴 문제를 구분한다. 화면 확인을 하지 못했다면 사용자가 누를 버튼과 기대 결과를 제시한다. 문서만 바뀌면 링크와 내용의 일관성을 확인한다.
5. 기억 동작을 바꾼 경우에는 해당 역할의 조건이 저장되는지, 다른 역할로 갔다 돌아와도 남는지, 수정 후 해당 활동의 브리핑만 바뀌는지 확인한다. 새로고침이나 참가자 초기화에 영향을 주는 작업이면 기존 데이터와 초기화용 복구 사본도 함께 점검한다.

### 4. PR 초안과 GitHub Desktop 안내

작업이 끝났거나 사용자가 PR을 요청하면, 현재 변경 내용을 읽어 **커밋 제목, PR 제목, 붙여 넣을 PR 본문**을 작성한다. 작업 브랜치에 이미 올린 변경이 있다면 그 기록도 읽고 `main`에 새로 들어갈 변경 전체를 반영한다. 변경을 볼 수 없으면 아래 틀에 따라 초안을 만들되, 모르는 내용은 ‘확인 필요’로 둔다.

```markdown
## 바꾼 내용
- 이전에 어떤 상황에서 문제가 있었고, 이제 화면에서 무엇이 달라지는지 적습니다.

## 확인 방법
1. 시작 화면과 눌러야 할 버튼을 적습니다.
2. 성공하면 보여야 할 결과를 적습니다.

## 검증 결과
- 빌드, 코드 점검, 실제 화면 중 확인한 항목과 결과를 적습니다.
- 남은 확인이나 기존 경고가 있다면 적습니다.

## 리뷰 전에 볼 내용
- 관련 이슈, 먼저 합칠 PR, 필요한 스크린샷이 있을 때만 적습니다.
```

사용자에게는 **현재 상태에서 필요한 단계만** 안내한다.

1. 커밋 전이면 GitHub Desktop에서 `Current Branch`가 내 작업 브랜치인지 확인한다. `Changes`에서 이번 작업에 해당하는 파일만 선택하고, 제안한 제목을 `Summary`에 넣어 `Commit to …`를 누른다.
2. 처음 올리는 브랜치라면 `Publish branch`, 이미 올린 브랜치라면 `Push origin`을 누른다. 푸시한 내용은 원격 작업 브랜치에 올라간다. `main`에 반영되는 시점은 PR을 합칠 때다.
3. 새 PR이라면 `Create Pull Request`를 눌러 GitHub를 연다. `base: main`, `compare: 내 작업 브랜치`인지 확인하고 제목과 본문을 넣는다. 이미 열린 PR에 수정한 경우 같은 브랜치에 다시 푸시하면 PR이 갱신된다.
4. 팀원 한 명에게 확인 방법대로 눌러보도록 요청한다. 통합 담당이 검토 결과와 최신 버전에서의 동작을 보고 합친다.

‘PR 써줘’는 붙여 넣을 초안을 작성하라는 뜻으로 해석한다. 커밋, 원격 푸시, 실제 PR 생성, 병합은 팀원이 수행하는 흐름이 기본이다. `main` 직접 푸시와 강제 푸시는 피한다. `main`에서 실수로 수정했거나 커밋했다면 현재 변경을 보존한 채 상태에 맞는 복구를 안내한다. 변경 삭제나 기록 덮어쓰기로 해결하지 않는다.

### 5. 충돌이나 오류가 났을 때

- **최신 변경을 먼저 받으라는 메시지.** 브랜치 이름과 변경 상태부터 확인한다. 안전하게 저장된 상태라면 최신 `main`을 받은 뒤 작업 브랜치에서 `Update from main`으로 반영하는 방법을 안내한다. 상대 변경을 덮는 푸시는 안내하지 않는다.
- **같은 파일에서 충돌.** 두 사람이 만들려던 화면 동작을 확인한다. 실제 충돌 내용을 읽고 필요한 변경이 모두 살아 있는 해결안을 검증한다. 판단하기 어렵다면 충돌 파일명과 각 변경의 목적을 적어서 작업자와 통합 담당이 함께 볼 수 있게 한다. 수정 후 검증과 커밋·푸시를 거쳐 기존 PR을 갱신한다.
- **병합 후 앱이 깨짐.** 통합 담당에게 재현 순서, 해당 PR, 마지막 정상 버전을 정리해준다. 세션이 임박했다면 보관한 정상 UT 버전을 사용하고, 별도 수정 PR이나 되돌리기 PR을 검토한다.

### 6. 팀원에게 마무리로 남길 것

기능 작업을 끝냈다면 **달라진 화면 동작 → 확인 결과와 남은 확인 → 지금 누를 다음 버튼 → 필요하면 PR 초안** 순서로 짧게 답한다. 문구 검토나 버튼 질문이라면 해당 답만 준다. 팀원이 볼 수 없는 기술 정보는 작업에 필요한 만큼만 설명한다.

팀은 이 파일의 최신본을 한 곳에서 관리한다. 저장소 준비 후에는 팀이 접근할 수 있는 한 위치에 두고, 새 대화에는 그 버전을 첨부한다. 담당자와 일정처럼 자주 바뀌는 내용은 작업표에서 확인한다.
